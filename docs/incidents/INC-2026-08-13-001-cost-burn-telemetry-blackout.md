## 根因分析

### 直接原因

```
ccg 会话 4 件事叠加：
1. 主模型 glm-5.2 单价高（¥4/¥16 每百万 token）
2. Claude Code 每轮重发完整历史 → 上下文 tokens 指数膨胀（32k-200k 档位）
3. tool_use 死循环：input_json_delta 修复前，Bash 参数丢失 → 模型反复重试
4. proxy 当时零护栏：无调用次数上限、无上下文长度上限
```

### 根本原因

```
1. 治理观测面错位：MAREF 治理观测"工具调用/状态机"，烧钱发生在"API 调用层"，两层无数据通路
2. 审计链可信度崩坏：测试代码直接写生产审计链（7.7 万条自转），真实信号被淹没
3. 看门狗自我续命：check_audit_log_growth 在日志 stale 时"先 touch 再自查"，永远通过
4. HMAC key 分发失败：sidecar 无 key，fail-closed 静默落 stdout → 4 天审计断裂无告警
5. 遥测链路仓库错位：看门狗/飞轮/遥测导出器全在闭源 openclaw 侧，开源部署零遥测零上报（信任崩塌根源）
```

### 5 Whys 分析

| Why | 回答 |
|-----|------|
| Why 1: 事件为什么会发生？ | 高价模型 + 上下文膨胀 + tool_use 死循环 + proxy 零护栏四件事叠加，成本失控 |
| Why 2: 为什么会存在这个条件？ | proxy 是独立进程，与 MAREF 治理零耦合，API 调用层不在治理观测范围内 |
| Why 3: 为什么没有提前发现？ | 遥测端点不可达、ObsPipeline 是死代码、ObsBridge 未接线、飞轮停摆——遥测链从采集到上报全部失效 |
| Why 4: 为什么防护措施没起作用？ | 看门狗"自我续命"（stale 时自己 touch 再自查）；审计链被测试污染无真实信号可检测 |
| Why 5: 为什么流程/系统允许这种情况？ | 运营能力（看门狗/飞轮/遥测）保留在闭源侧，开源部署无"神经系统"；且审计 key 分发无统一入口 |

### 触发条件

- **首次触发**: 2026 年 8 月 9 日前后（遥测断裂起点；成本失控的确切起点需账单数据确认）
- **触发事件**: ccg 高频会话持续使用 glm-5.2，上下文重复膨胀 + 工具调用死循环
- **告警是否生效**: ☑ 否（无任何成本/遥测/审计断裂告警；看门狗因自我续命逻辑误报 healthy）

## 处置回顾

### 做得好 👍

1. 账单审计发现成本异常后，当日即在 proxy 层落地 CALL-GUARD / CTX-GUARD 两道有效护栏
2. 审计复盘没有停在"proxy 没护栏"的表面，深挖到治理观测面错位、审计链污染、看门狗自我续命、遥测仓库错位 4 类结构性根因
3. 全部根因都有代码级证据（grep / 日志 / 端点探测），非推测

### 做得不好 👎

1. API 调用层长期处于治理视野之外，proxy 与 MAREF 零联动
2. 测试/压力/混沌脚本直接写生产审计链，污染 7.7 万条
3. 看门狗存在"自我续命"逻辑，健康检查失去意义
4. HMAC key 分发不一致，sidecar 静默失去审计能力 4 天无人发现
5. 全域数据飞轮、遥测端点、ObsBridge 接线全部停摆/死代码，遥测形同虚设

### 改进点 🔧

1. 打通 API 调用层与治理层（cost_event 入审计链 + usage 端点 + M4 成本检查）
2. 修复看门狗自我续命逻辑（真实事件存在性检查）
3. 测试隔离（MAREF_AUDIT_PATH 强制 /tmp）
4. HMAC key 统一分发 + fail-closed 显式告警
5. 遥测链路整体修复（端点可用性、ObsBridge 接线、飞轮治理相位）——详见补强实施方案

# MAREF 灰度发布方案

## 1. 概述

本文档定义了 MAREF 的灰度发布策略，采用渐进式放量方式，从 10% 用户逐步扩展到 100%，确保在每阶段都能及时发现问题并回滚。

## 2. 灰度发布策略

### 2.1 放量阶段

| 阶段 | 放量比例 | 持续时间 | 决策点 |
|------|---------|---------|--------|
| Phase 0 | 内部白名单 | 按需 | 内部验证通过 |
| Phase 1 | 10% | 30 分钟 | 监控无异常 |
| Phase 2 | 25% | 60 分钟 | 监控无异常 |
| Phase 3 | 50% | 120 分钟 | 监控无异常 |
| Phase 4 | 100% | - | 全量发布完成 |

### 2.2 内部白名单

发布前选择内部用户和测试账号组成白名单，通过 Feature Flag 的 whitelist 机制绕过灰度百分比限制，实现 100% 覆盖验证。

## 3. 功能开关设计

### 3.1 Feature Flag 定义

| Flag 名称 | 说明 | 默认状态 |
|-----------|------|---------|
| canary_release | 灰度发布总开关 | 关闭 |
| new_governance_engine | 新治理引擎 | 关闭 |
| enhanced_audit | 增强审计 | 关闭 |
| real_time_monitoring | 实时监控 | 关闭 |
| auto_rollback | 自动回滚 | 关闭 |
| advanced_drift_detection | 高级漂移检测 | 关闭 |
| desktop_agent_v2 | 桌面 Agent V2 | 关闭 |
| mcp_protocol_v2 | MCP 协议 V2 | 关闭 |

### 3.2 灰度实现

基于用户 ID 哈希实现灰度放量：

```
hash(user_id) % 100 < rollout_percentage
```

- 相同用户 ID 始终映射到同一灰度分组
- 白名单用户绕过百分比限制
- 支持动态调整放量比例

### 3.3 配置持久化

Feature Flag 配置存储在 JSON 文件中，支持运行时动态加载和保存。

## 4. 灰度发布流程

### 4.1 标准流程

```
1. Feature Flag on 10%
   ├── 启用目标功能的 Feature Flag
   ├── 设置 rollout_percentage = 10
   ├── 添加白名单用户确保内部验证
   └── 启动监控

2. 监控 30 分钟
   ├── 观察错误率、延迟、覆盖率等指标
   ├── 确认无 P0 告警
   └── 记录监控数据

3. 无异常扩至 25%
   ├── 调整 rollout_percentage = 25
   ├── 持续监控 60 分钟
   └── 确认指标在阈值范围内

4. 无异常扩至 50%
   ├── 调整 rollout_percentage = 50
   ├── 持续监控 120 分钟
   └── 确认指标在阈值范围内

5. 全量发布 100%
   ├── 调整 rollout_percentage = 100
   ├── 持续监控
   └── 确认发布完成
```

### 4.2 快速回滚

任何阶段触发回滚条件时：

```
1. 检测到异常指标或告警
2. 执行回滚操作
   ├── 设置 rollout_percentage = 0
   ├── 或执行 git checkout 到上一个稳定版本
   └── 或执行 K8s 回滚到上一个镜像版本
3. 验证回滚后服务健康
4. 记录回滚原因和时间戳
```

## 5. 监控指标

### 5.1 关键指标

| 指标 | 正常阈值 | 告警阈值 | 回滚阈值 |
|------|---------|---------|---------|
| 错误率 | < 0.5% | < 1% | >= 1% |
| P99 延迟 | < 200ms | < 500ms | >= 1s |
| P95 延迟 | < 100ms | < 300ms | >= 500ms |
| 测试覆盖率 | >= 75% | >= 70% | < 70% |
| 内存增长 | < 3%/24h | < 5%/24h | >= 10%/24h |
| CPU 使用率 | < 60% | < 80% | >= 90% |

### 5.2 告警级别

| 级别 | 说明 | 响应时间 |
|------|------|---------|
| P0 | 服务不可用 / 数据丢失 | 立即响应 |
| P1 | 核心功能异常 | 15 分钟内 |
| P2 | 非核心功能异常 | 1 小时内 |
| P3 | 告警通知 | 24 小时内 |

### 5.3 监控工具

- Grafana Dashboard: `configs/grafana/maref-dashboard.json`
- OpenTelemetry: 通过 Sidecar 收集指标
- 审计日志: 通过 AuditLogger 记录所有变更

## 6. 回滚触发条件

### 6.1 自动回滚条件

任何以下条件触发自动回滚：

- **P0 告警**: 服务不可用、核心链路中断、数据丢失
- **错误率 > 1%**: 持续 2 分钟以上
- **P99 延迟 > 1s**: 持续 5 分钟以上
- **内存增长 > 10%/24h**: 持续 30 分钟以上
- **测试覆盖率下降 > 5%**: 低于 70%

### 6.2 手动回滚条件

- 功能行为不符合预期
- 用户体验明显下降
- 安全漏洞被发现
- 合规检查不通过

### 6.3 回滚步骤

```bash
# 方式一：Feature Flag 回滚
maref feature set canary_release rollout_percentage 0

# 方式二：K8s 回滚
./scripts/rollback.sh v0.25.0 --verify

# 方式三：本地回滚
./scripts/rollback.sh v0.25.0 local --verify

# 方式四：灰度回滚（仅回滚部分实例）
./scripts/rollback.sh v0.25.0 --canary=25
```

## 7. 灰度发布检查清单

### 7.1 发布前检查

- [ ] Feature Flag 已创建并配置
- [ ] 监控告警已配置
- [ ] 回滚脚本可执行
- [ ] Runbook 已更新
- [ ] 应急联系人已通知
- [ ] 测试覆盖率 >= 75%
- [ ] 类型检查 0 错误
- [ ] 安全扫描 0 High/Critical

### 7.2 灰度中检查

- [ ] Phase 0 白名单验证通过
- [ ] Phase 1（10%）监控 30 分钟无异常
- [ ] Phase 2（25%）监控 60 分钟无异常
- [ ] Phase 3（50%）监控 120 分钟无异常
- [ ] 每个阶段记录监控数据

### 7.3 全量发布后检查

- [ ] 错误率 < 0.5%
- [ ] P99 延迟 < 200ms
- [ ] 内存增长 < 3%/24h
- [ ] 审计日志完整
- [ ] 回滚脚本已验证

## 8. 与 Go/No-Go 决策流程对接

灰度发布是 Go/No-Go 决策流程的 M4 运维就绪门禁的一部分：

### 8.1 决策对接流程

```
Go/No-Go 决策流程
│
├── M1 工程质量 ──── 测试覆盖率、类型检查、代码风格
├── M2 安全合规 ──── SAST 扫描、依赖漏洞、密钥管理
├── M3 性能体验 ──── API 延迟、Lighthouse 评分、内存增长
│
├── M4 运维就绪 ──── 灰度发布方案 + 功能开关
│   ├── 4.9 灰度发布方案 ── docs/canary-release-plan.md
│   ├── 4.10 功能开关 ──── src/maref/features/feature_flags.py
│   └── 灰度发布完成方可进入下一阶段
│
├── M5 产品就绪 ──── 版本对齐、CHANGELOG
│
└── 决策: GO / NO-GO
```

### 8.2 灰度发布决策点

每个放量阶段结束后，由运维负责人确认：

- **指标是否在阈值范围内**: 是 / 否
- **是否存在未解决告警**: 是 / 否
- **是否继续下一阶段**: 是 / 否（回滚）

### 8.3 回滚后处理

回滚后需执行：

1. 记录回滚原因和时间戳
2. 更新 incident-postmortem-template.md
3. 修复问题后重新执行灰度发布流程
4. 在 Go/No-Go 决策表中记录回滚事件
